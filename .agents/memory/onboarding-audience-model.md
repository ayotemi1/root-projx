---
name: Onboarding audience model
description: The distinct acquisition and access model for supporters and organisation representatives.
---

Supporters create an account immediately and continue into discovery and giving. Organisation representatives create their own login while submitting an application; their organisation tools remain locked until approval.

**Why:** Combining both audiences in one registration flow created contradictory expectations, duplicated organisation details, and made the two journeys feel interchangeable.

**How to apply:** Route supporter acquisition to immediate registration and organisation acquisition to account creation plus review. Never generate a temporary password on approval; activate the applicant's existing account instead.

Supporter interests are optional and private. Use the organisation-profile
sector list, never preselect choices, and keep existing sign-in independent of
onboarding. Supporters must be able to change or clear interests in Settings.

**Why:** The user explicitly requested an optional post-registration step,
not a new barrier for returning supporters or a public profile attribute.

**How to apply:** Do not force completion, expose interests publicly, or claim
personalised suggestions before a matching feature actually uses them.

Supporter onboarding is Create account → Interests → Follow a few organisations
→ Home. Both preference steps are optional; skipping the follows step must keep
any follows already saved. Suggestions should prefer selected profile sectors
and fill remaining places with real public organisations, never example cards.

**Why:** The user wants a low-pressure introduction using real organisations,
not a minimum-follow gate or a reset of choices when someone skips.

**How to apply:** Preserve ordinary returning-supporter sign-in and keep both
onboarding exit actions available even with zero follows or a loading error.

Approved organisations should manage their own profiles and launch campaigns
without Root ProjX editing their content. Root ProjX's manual gates are application
approval and confirmation of an off-platform bank-transfer payout arrangement.

**Why:** The user states that organisation onboarding is outgrowing the team's
capacity to hand-hold each organisation.

**How to apply:** Design organisation tools for independent use, with saved-data
publish gates rather than an additional manual campaign-review requirement.

Organisation representatives commonly use phones on slow connections. Treat
390px usability and recovery from interrupted editing as requirements, not
optional polish. Guided setup must advance on confirmed real actions/data,
never merely on clicking through instructions.

**Why:** The self-service specification explicitly identifies these working
conditions and requires that organisations can leave and resume without losing
their work.

**How to apply:** Preserve unfinished edits on failures, distinguish drafts from
confirmed saved data, and keep optional sections optional when deciding whether
a profile is ready.

The organisation application uses
`attached_assets/rootprojx-organisation-application_1795471394034.html` as its
visual reference and starts directly with the organisation-details step, without
a welcome screen.

**Why:** On 2026-11-23 the user explicitly requested this reference as a
presentation-only change, preserving every field, validation rule, submission
contract and approval restriction.

**How to apply:** Keep future application restyles within those boundaries.
This reference is for organisation applications, not supporter registration.
